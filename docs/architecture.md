# Architecture

Cross-cutting reference for how Service Nova is wired. Feature-specific behavior lives in [features/](features/).

## Stack

| Concern | Choice |
| --- | --- |
| Build | Vite 5 + `@vitejs/plugin-react`, TypeScript 5.6 |
| Routing | TanStack Router, file-based (`src/routes/`), route tree generated by `TanStackRouterVite()` |
| Server state | TanStack Query v5 |
| Backend | Firebase — Auth (Google provider) + Firestore |
| UI | NextUI v2, Tailwind CSS, framer-motion, `@tabler/icons-react` |
| Feedback | react-toastify |
| Offline | `vite-plugin-pwa` (Workbox) |

## Provider stack

`src/main.tsx` builds the router and nests the providers:

```
StrictMode
└── QueryClientProvider (client from src/lib/react-query.ts)
    └── NextUIProvider locale="en-GB"     ← makes DatePicker parse/render day-first
        ├── RouterProvider (router with { queryClient } context)
        └── ReactQueryDevtools
```

The router is created with `context: { queryClient }`, which is what lets route loaders call `queryClient.ensureQueryData(...)`. `defaultPreload: "intent"` prefetches on link hover.

`src/routes/__root.tsx` renders the `<Outlet />` plus the global `<ToastContainer theme="dark" position="top-right" />`.

Query client defaults (`src/lib/react-query.ts`): `staleTime` 5 minutes, `gcTime` 1 hour.

## Firestore data model

```
vehicles/{vehicleId}
  make: string
  model: string
  year: number
  plate: string
  imageUrl?: string          ← a URL typed by the user, not an upload
  nextServiceDate?: Timestamp | null   ← denormalized from the latest saved service

  services/{serviceId}       ← subcollection
    date: Timestamp
    mileage: number
    price: number
    serviceType: string
    notes: string
    nextServiceDate: Timestamp | null
```

TypeScript mirrors of this live in `src/types/vehicle.type.ts` (`TVehicle`, `TVehicleWithServices`) and `src/types/service.type.ts` (`TService`). In TypeScript the date fields are `Date`, not `Timestamp` — see the boundary below.

Firebase Storage is initialized in `src/config/firebase.ts` and exported, but nothing imports it; vehicle images are plain URLs.

`db` is built with `initializeFirestore(app, { localCache: persistentLocalCache({ tabManager: persistentMultipleTabManager() }) })`, not plain `getFirestore`. Reads fall back to IndexedDB when the network is gone and writes queue for replay — see [features/pwa-offline.md](features/pwa-offline.md).

## The read path

Everything on screen comes from **one** query.

`src/services/useFetchVehicles.ts`:

1. `getDocs(query(collection(db, "vehicles")))` — all vehicles, unfiltered (this is a shared family garage, see [features/vehicles.md](features/vehicles.md)).
2. `Promise.all` over those vehicles, each fetching `vehicles/{id}/services`.
3. Timestamps converted to `Date` via `firebaseTimestampToDate`.
4. Each vehicle's services sorted newest-first.
5. Exposed as `vehiclesQueryOptions` — query key **`["vehicles"]`**, returning `TVehicleWithServices[]`.

Step 2 is one read per vehicle. A `collectionGroup(db, "services")` query would collapse them into a single read, but the deployed rules scope services to `/vehicles/{vehicle}/services/{serviceId}`, and a collection-group query is only permitted by a rule matching `/{path=**}/services/{serviceId}`. Don't switch to one without changing the rules first — the query fails closed and service history silently comes back empty.

Consumers:

- `src/routes/_auth/dashboard.tsx` — `loader: ensureQueryData(vehiclesQueryOptions)`, and `Dashboard` reads it back with `DashboardRoute.useLoaderData()`.
- `src/routes/_auth/vehicles.tsx` — `useQuery(vehiclesQueryOptions)`, no loader.
- `src/routes/_auth/vehicles_/$vehicleId.tsx` — `useQuery(vehiclesQueryOptions)` then `.find(v => v.id === vehicleId)`. There is no single-vehicle fetch.

This is why the whole app stays in sync from one cache entry — and why every mutation has to keep `["vehicles"]` correct.

## The write path

One hook per operation in `src/services/`, each a `useMutation` that talks to Firestore directly and toasts the outcome:

| Hook | Firestore call | Cache strategy |
| --- | --- | --- |
| `useAddVehicle` | `setDoc(vehicles/{newId})` | `refetchQueries(["vehicles"])` |
| `useUpdateVehicle` | `updateDoc(vehicles/{id})` | `refetchQueries(["vehicles"])` |
| `useDeleteVehicle` | batched delete of the `services` subcollection, then `deleteDoc(vehicles/{id})` | `setQueryData` — filters the vehicle out |
| `useAddService` | `setDoc(services/{newId})` **+** `updateDoc(vehicle.nextServiceDate)` *only when newest* | `setQueryData` — inserts the service and re-sorts |
| `useUpdateService` | `updateDoc(services/{id})` **+** `updateDoc(vehicle.nextServiceDate)` *only when newest* | `refetchQueries(["vehicles"])` |
| `useDeleteService` | `deleteDoc(services/{id})` | `setQueryData` — filters the service out and recomputes `nextServiceDate` |

`useAddVehicle` / `useUpdateVehicle` import the module-level `queryClient` from `src/lib/react-query.ts`; the others use the `useQueryClient()` hook. Both reach the same client.

**Every write goes through `settleLocally`** (`src/services/settleLocally.ts`). A Firestore write promise only settles on the server ack, which never arrives offline, so awaiting one there hangs the mutation. `settleLocally(value, ack)` resolves as soon as the write is in the local cache and surfaces a genuine server rejection as a late error toast. Two consequences worth knowing before you add a hook:

- The two "add" hooks mint the document id client-side with `doc(collection(db, path))` and call `setDoc`, rather than awaiting `addDoc` for the id.
- A hook's `onError` only sees synchronous failures; server rejections arrive through `settleLocally`.

Use `savedToast` from the same module for success toasts — it appends "will sync when you're back online" while offline.

## The Timestamp ↔ Date boundary

Firestore stores `Timestamp`; React components want `Date`; NextUI's `DatePicker` wants `CalendarDate` from `@internationalized/date`. `src/utils/formatDate.ts` owns the first conversion:

- `firebaseTimestampToDate(ts)` — on the way in (`useFetchVehicles`, `useAddService`'s cache patch).
- `dateToFirebaseTimestamp(date)` — on the way out (the service form).
- `formatDate(date)` — `dd-mm-yyyy`, used in compact spots (cards, dashboard).
- `formatDateToLongDate(date)` — `5 September 2026`, used in headings and metric cards.

`CalendarDate` conversion happens inline in `src/features/vehicle-details/service-form-modal.tsx`: `parseDate(date.toISOString().split("T")[0])` in, `new Date(calendarDate.toString())` out.

## Routing

File routes in `src/routes/`:

| File | URL | Notes |
| --- | --- | --- |
| `index.tsx` | `/` | `beforeLoad` awaits `authService.waitForUser()`, then redirects to `/vehicles` or `/login` |
| `login.tsx` | `/login` | Same wait, then redirects signed-in users to `/vehicles` |
| `_auth.tsx` | — | Pathless guarded layout: loader requires a user, else `redirect({to:"/login"})`; renders `MainLayout` |
| `_auth/dashboard.tsx` | `/dashboard` | Prefetches vehicles in its loader |
| `_auth/vehicles.tsx` | `/vehicles` | Vehicle grid |
| `_auth/vehicles_/$vehicleId.tsx` | `/vehicles/:vehicleId` | The trailing `_` on `vehicles_` opts the detail page **out** of nesting under `/vehicles`, so it renders standalone instead of inside the list route |

`src/routeTree.gen.ts` is generated — add a file under `src/routes/` and the plugin regenerates it. Never edit it by hand.

## Path alias

`vite.config.ts` maps `@` → `src`, but every import in the codebase is relative. Stay relative unless you convert the whole tree.
